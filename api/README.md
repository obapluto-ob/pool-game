# Authentication and Community deployment

The authentication endpoint is a Vercel Function at `/api/auth`. It uses Firebase Admin to store server-side PIN hashes and issue Firebase custom tokens. Google sign-in uses Firebase's browser SDK and the allowlisted public config returned by `/api/firebase-config`. Google accounts can create a FELTORA username or be linked to an existing username/PIN account from the profile panel.

Before deploying:

1. Add the Firebase Admin service-account JSON to Vercel as `FIREBASE_SERVICE_ACCOUNT_JSON`. Never commit this credential or paste it into chat.
2. Set `FIREBASE_DATABASE_URL` to the Realtime Database URL for the same Firebase project. The auth endpoint uses `FIREBASE_WEB_CONFIG.databaseURL` when this variable is omitted; the payment webhook falls back to the FELTORA database URL. Auth compares normalized URLs, ignoring surrounding whitespace, hostname casing, and trailing slashes.
3. Set `FIREBASE_WEB_CONFIG` to the Firebase **Web app config JSON** from Project settings → General → Your apps. It needs `apiKey`, `authDomain`, `projectId`, and `appId`; include the database URL and other public fields from the same project when available. This is public client configuration, not the Admin service-account JSON.
4. In Firebase Console → Authentication, enable the Google provider and add the production hostname (for example, `pool-game-gamma.vercel.app`) and the local development hostname (`127.0.0.1` or `localhost`, as used) to the authorized domains list. The domain in the browser address bar must be authorized for popup and redirect sign-in.
5. Ensure Firebase Authentication and the Realtime Database are enabled for that project. The browser config, Admin credentials, and `FIREBASE_DATABASE_URL` must all refer to the same Firebase project and database.
6. Publish [firebase-rules.json](../firebase-rules.json) to Realtime Database Rules before enabling the Community UI. Deploying the website to Vercel does **not** publish Firebase rules. Guests can read community posts; authenticated users can create, like, follow, or delete their own posts. Private player messages are stored under a room key made from the two Firebase UIDs, require an authenticated Firebase session, and are readable only by either participant. A per-user, participant-only index makes new conversations discoverable in the Messages inbox. Players can start a chat from a Community post or find a player by username in Contacts. A player who likes somebody else's post creates a notification readable only by the post owner. Legacy username-keyed messages are not migrated.
7. Set `PAYSTACK_SECRET_KEY` in Vercel and configure Paystack to send signed webhook events to `/api/paystack-webhook`. Developer tips are verified before the thank-you screen and supporter badges/tip cosmetics are granted by the signed webhook, not by the browser callback. Wallet top-ups use `/api/wallet`, are KES-only, start at KSh 100, and credit 10 game credits per KSh only after the server verifies the Paystack transaction. The wallet supports purchases of listed cosmetics and player-to-player game-credit transfers; credits cannot be withdrawn or exchanged for cash. The in-game Activity app retains recent wallet transactions and community-like notifications; it checks for updates while the player is online, displays an in-app badge/toast, and is not operating-system push notification delivery. The Contacts app searches exact usernames through the authenticated wallet API. Keep `wallets`, `walletPaymentIntents`, `walletPaymentEvents`, and `walletTransfers` private in Realtime Database Rules; the included rules deny direct client access.
8. Deploy through Vercel using Node.js 22.x, as configured in `package.json`. Firebase Admin is pinned to 13.10.0 so its `jwks-rsa` dependency uses CommonJS-compatible `jose`; Firebase Admin 14 pulled ESM-only `jose`, which crashes the Vercel CommonJS function bundle. The existing Netlify configuration serves static files and does not deploy these `/api` functions.

For the tournament Join action, include the host's Firebase UID as `hostUid` in `/tournament/active`; the app resolves the host profile and sends a direct message.

Google sign-in uses a popup on desktop and a redirect on narrow screens. New Google users choose a FELTORA username and a four-digit PIN; both credentials resolve to the same Firebase UID, so they can sign in on another device with Google or with username and PIN. Existing Google users who return on a device with a saved Firebase session see their username and can choose to continue; accounts created before PIN setup remain usable with Google. Existing PIN users can sign in and choose **Link Google for easier sign-in** in their profile; this keeps the same Firebase UID and profile. The browser's Firebase auth persistence restores the Google session on the same device. Four-digit PINs are weak; Google sign-in remains the recommended option.

If Community requests return `401 Permission denied`, verify the deployed Realtime Database rules on the exact database URL configured by `FIREBASE_WEB_CONFIG`. The source rules allow public Community reads, but a Vercel deployment alone does not apply them. Publish the updated `firebase-rules.json` separately in Firebase Console; wallet records are server-only and should not receive client read/write permissions. Publishing the updated rules also changes private messages from username-based public rooms to authenticated UID-based participant rooms; deploy these rules for private-message access control to take effect.

If Google sign-in succeeds but choosing a FELTORA username fails, the browser sends `google-register` to `/api/auth`. Check the Vercel Function logs and confirm `FIREBASE_SERVICE_ACCOUNT_JSON`, `FIREBASE_WEB_CONFIG`, and `FIREBASE_DATABASE_URL` are configured for the same Firebase project. The Admin service account must be valid and have access to that project's Realtime Database. Missing, invalid, or mismatched server credentials return a configuration error; other server failures are logged by the function. The `contentscript.js` listener warnings are from a browser extension, and the Firebase popup COOP warnings are separate from an `/api/auth` response.

The existing four-digit PIN is low-entropy and has no recovery channel. The function rate-limits failed sign-ins, but this should not be treated as strong account security. Profile settings, progression, points, and owned cosmetics sync through Firebase; game result stats remain local-only. Weekly leaderboard wins are client-reported and are not independently verified. Historical local-only posts are not uploaded or treated as verified during migration.
